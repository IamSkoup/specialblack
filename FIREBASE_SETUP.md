# Подключение Firebase к SpecialBlack

В исходном `index.html` Firebase не был подключён, поэтому конфигурация создаётся с нуля.
Всё, что описано ниже, нужно сделать один раз.

## Что изменилось в файлах проекта

- **index.html** — добавлены: шапка с входом/профилем/уведомлениями, модальные окна (вход,
  регистрация, профиль, заказ, отзыв, все отзывы, админ-панель), блок предоплаты в тарифах,
  раздел FAQ, динамические отзывы на главной, и один `<script type="module">` в самом низу
  файла — это и есть весь код работы с Firebase.
- **database.rules.json** — правила безопасности Realtime Database. Скопировать их в консоль
  Firebase (см. шаг 5).
- **storage.rules** — правила безопасности Storage для аватаров (см. шаг 6).

Внутри `index.html` найдите блок `/* === 1. КОНФИГУРАЦИЯ === */` — туда нужно вставить свои
значения (шаг 3) и при желании поменять `TELEGRAM_USERNAME`, `ADMIN_EMAIL`.

## Шаг 1. Создать проект Firebase

1. Откройте [console.firebase.google.com](https://console.firebase.google.com) → **Add project**.
2. Введите название (например, `specialblack`), пройдите мастер создания (Google Analytics не
   обязателен).

## Шаг 2. Включить нужные сервисы

В левом меню консоли, раздел **Build**:

1. **Authentication** → **Get started** → вкладка **Sign-in method** → включите **Email/Password**
   (переключатель «Email/Password», Save). Больше никакие способы входа не нужны.
   - Там же вкладка **Templates** → можно отредактировать текст письма «Email address
     verification» (необязательно, работает и со стандартным текстом).
   - Вкладка **Settings → Authorized domains** — добавьте домен, на котором будет жить сайт
     (например, `ваш-логин.github.io`), иначе вход/регистрация не будет работать на реальном домене.
2. **Realtime Database** → **Create Database** → выберите регион → любой начальный режим
   (правила всё равно будут полностью заменены на шаге 5).
3. **Storage** → **Get started** → Production mode → выбрать тот же регион.
   Нужен для аватаров профиля.
4. Cloud Functions в этой версии **не используются** — всё реализовано через Firebase Security
   Rules, без отдельного backend-сервера (детали и границы такого подхода — в конце документа).

## Шаг 3. Добавить веб-приложение и получить конфигурацию

1. На главной странице проекта нажмите иконку **`</>`** (Add app → Web).
2. Задайте имя приложения, **Firebase Hosting подключать не обязательно**.
3. Появится объект `firebaseConfig` — скопируйте его целиком.
4. Откройте `index.html`, найдите:
   ```js
   const firebaseConfig = {
     apiKey: "ВАШ_API_KEY",
     ...
   };
   ```
   и замените на свой объект.

**О публичности значений**: `apiKey`, `authDomain`, `projectId` и остальные поля
`firebaseConfig` — это **не секретные** ключи, это публичные идентификаторы проекта; они и так
видны любому в исходном коде сайта. Реальная защита данных обеспечивается Security Rules
(шаги 5–6), а не секретностью этого объекта. Не подключайте новую отдельную Firebase-конфигурацию
позже — если понадобится что-то поменять, редактируйте именно эти значения.

## Шаг 4. Структура данных Realtime Database

Проект использует такие узлы (создаются автоматически кодом сайта, вручную создавать не нужно,
кроме `admins`, см. шаг 7):

```
users/{uid}                → профиль: nickname, email, avatarUrl, createdAt, ordersCount, completedCount, reviewsCount
orders/{orderId}           → заказы (структура — по ТЗ: orderId, userId, selectedTariff, basePrice,
                              logo, logoPrice, totalPrice, prepaymentAmount, remainingAmount,
                              paymentStatus, questionnaire {...}, status, adminComment, clientComment,
                              completedAt, cancelledAt, promoCode, discountAmount, displayId)
reviews/{reviewId}         → отзывы: rating, text, userId, userNickname, userAvatar, orderId, published
reviewsByOrder/{orderId}   → orderId → reviewId (техническая связка "у заказа уже есть отзыв")
notifications/{uid}/{id}   → внутренние уведомления пользователя
promoCodes/{code}          → промокоды: discountType, discountValue, expiresAt, maxUses, usedCount, active
admins/{uid}                → true — если пользователь администратор (см. шаг 7)
```

## Шаг 5. Установить Realtime Database Rules

1. **Realtime Database → Rules**.
2. Вставьте содержимое файла `database.rules.json` целиком (замените всё, что там есть).
3. **Publish**.

Что делают эти правила, коротко:
- Профиль (`users/{uid}`) редактирует только сам пользователь (или админ); поле
  `completedCount` может менять только админ.
- Заказ создаёт только авторизованный пользователь на себя же (`userId` должен совпадать с
  `auth.uid`), причём `basePrice` обязан соответствовать выбранному тарифу из зафиксированного
  списка цен, `logoPrice` — 0 или 200 строго в связке с полем `logo`, `totalPrice` —
  `basePrice + logoPrice − discountAmount`, `prepaymentAmount` — ровно половина от `totalPrice`
  (с округлением), `remainingAmount` — остаток. Статус нового заказа обязан быть `pending`.
- После создания пользователь **не может** менять заказ, кроме перевода `pending`/`confirmed` →
  `cancelled`. Все остальные изменения (статус, оплата, комментарии, даты, суммы) — только
  администратор.
- Отзыв можно создать только на **свой** заказ, только если его `status === completed`, и только
  один раз на заказ (проверяется через `reviewsByOrder`). Скрывать/удалять чужие отзывы обычный
  пользователь не может.
- `promoCodes` — читать может любой авторизованный (нужно для проверки кода при оформлении),
  писать — только админ.
- `admins/{uid}` — **никто не может писать через клиент** (`".write": false`), только вручную
  из консоли (шаг 7). Права администратора нельзя выдать себе через DevTools.

## Шаг 6. Установить Storage Rules

1. **Storage → Rules**.
2. Вставьте содержимое `storage.rules`.
3. **Publish**.

Это ограничивает загрузку аватаров: только сам пользователь, только в свою папку
`avatars/{uid}/...`, только JPG/PNG/WebP, не больше 3 МБ.

## Шаг 7. Назначить администратора (Кайон)

Права администратора **намеренно нельзя выдать через сайт** — ни через никнейм, ни через email в
коде. Единственный способ — вручную прописать UID в базе:

1. Попросите Кайона зарегистрироваться на сайте обычным способом, указав email
   `denisspesivcev8@gmail.com`, и подтвердить email по ссылке из письма.
2. В консоли Firebase откройте **Authentication → Users** — найдите строку с этим email,
   скопируйте значение **User UID**.
3. Откройте **Realtime Database → Data**, нажмите **+** рядом с корнем, создайте узел `admins`,
   внутри — узел с именем, равным скопированному UID, и значением **`true`** (тип boolean, не
   строка).
4. Готово — после обновления страницы у этого аккаунта появится иконка админ-панели в шапке
   сайта.

**Проверка**, что обычный пользователь не может стать админом: зарегистрируйте второй, обычный
аккаунт и попробуйте в консоли браузера выполнить что-то вроде
`set(ref(db,'admins/'+auth.currentUser.uid), true)` — запрос будет отклонён Security Rules
(`PERMISSION_DENIED`), поскольку `admins/$uid` имеет `".write": false` для всех.

## Шаг 8. Проверить сценарий целиком

1. Регистрация нового аккаунта → письмо с подтверждением пришло на почту.
2. Пока email не подтверждён — при попытке заказать сайт показывается экран с просьбой
   подтвердить email и кнопкой повторной отправки письма.
3. После подтверждения — вход, изменение никнейма/аватара/пароля в «Профиль → Настройки».
4. Выбор тарифа → в анкете отмечается «Логотип +200 ₽» → сумма в блоке «Условия оплаты»
   пересчитывается автоматически (итого / предоплата 50% / остаток).
5. «Создать заказ» → открывается экран с номером заказа и кнопкой «Продолжить в Telegram» —
   сообщение в Telegram уже заполнено (без пароля и других секретных данных).
6. Заказ появляется в «Профиль → Мои заказы» со статусом «Ожидает подтверждения».
7. Вход под аккаунтом Кайона (после шага 7) → иконка админ-панели в шапке → вкладка «Новые» →
   виден созданный заказ с полной анкетой → «Подтвердить».
8. В личном кабинете пользователя статус меняется на «Подтверждён», приходит уведомление
   (колокольчик в шапке).
9. Админ: «Предоплата получена» → «Взять в работу» → «Отметить выполненным» — на каждом шаге
   пользователю приходит уведомление, а в личном кабинете обновляется прогресс-шкала
   Создан → Подтверждён → В работе → Выполнен.
10. После `completed` в карточке заказа появляется кнопка «Оставить отзыв» — отправленный отзыв
    появляется на главной странице (в тройке последних) и в разделе «Все отзывы» с фильтрами по
    оценке и сортировкой; средний рейтинг и счётчик считаются автоматически.
11. Проверка отмены: создайте ещё один тестовый заказ и отмените его в статусе
    «Ожидает подтверждения» — появляется диалог подтверждения, статус меняется на «Отменён».
12. Проверка промокода: в админ-панели → «Промокоды» создайте `START10` (например, 10%,
    без срока, без лимита) → при оформлении нового заказа введите код — сумма пересчитается.
13. Попробуйте из DevTools отправить в базу заказ с явно завышенным `totalPrice` или с чужим
    `userId` — запись будет отклонена правилами (шаг 5).

## Важно понимать про безопасность расчётов

Правила Realtime Database (шаг 5) проверяют, что цена тарифа, цена логотипа, итоговая сумма,
50%-я предоплата и остаток совпадают с зафиксированной формулой — подделать их через DevTools
нельзя, как и подделать себе статус заказа, права администратора или чужой профиль.

Единственное место, где текущая реализация **не может** быть математически строго проверена
только правилами — это соответствие `discountAmount` конкретному промокоду (Realtime Database
Rules не умеют делать условные проверки со сравнением дат/типов скидки настолько гибко, чтобы на
100% исключить, что клиент пришлёт "скидку по промокоду", которая на 1–2 ₽ отличается от
настоящей). Итоговая сумма всё равно обязана сходиться с `basePrice + logoPrice − discountAmount`,
так что произвольно занизить цену без разумного предела нельзя, но точечная подмена скидки в
пределах суммы отдельного промокода теоретически возможна.

Если захотите закрыть это полностью — по ТЗ это как раз тот случай, когда правильное решение не
клиентский костыль, а **Cloud Function**: небольшая функция `createOrder` (HTTPS Callable),
которая сама читает тариф и промокод из базы, сама считает `totalPrice`/`prepaymentAmount` и уже
проверенные данные записывает в `orders/{orderId}`, а клиент вообще перестаёт присылать суммы.
Это не обязательно для запуска сайта — текущая защита на правилах закрывает все остальные
сценарии подмены данных, описанные в ТЗ (цена тарифа, статус заказа, чужой userId, права
администратора, дата выполнения, рейтинг отзыва).

## Что нужно сделать вручную в Firebase (сводка)

| Действие | Где | Что сделать |
|---|---|---|
| Включить вход по email | Authentication → Sign-in method | Включить провайдер Email/Password |
| Добавить домен сайта | Authentication → Settings → Authorized domains | Добавить домен, где опубликован сайт |
| Создать базу данных | Realtime Database → Create Database | Выбрать регион |
| Установить правила базы | Realtime Database → Rules | Вставить `database.rules.json`, Publish |
| Включить Storage | Storage → Get started | Production mode |
| Установить правила Storage | Storage → Rules | Вставить `storage.rules`, Publish |
| Назначить администратора | Realtime Database → Data | Создать `admins/{UID_Кайона} = true` вручную, после его регистрации |
| Вставить конфигурацию | `index.html`, блок КОНФИГУРАЦИЯ | Вставить `firebaseConfig` со страницы настроек веб-приложения |
